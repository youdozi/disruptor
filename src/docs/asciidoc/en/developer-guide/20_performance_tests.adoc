== Run the performance tests

When making changes to the Disruptor it is important to be aware of the performance impact of your change.

To measure the performance characteristics of the Disruptor there are many tests in the `perftest` and `jmh` sourcesets.

=== Running Perf Tests

The perf tests are all under `src/perftest` and are built using a custom framework.

To run them you need to fist build the perf jar and then run a single test at a time, for example:

[source,shell script]
----
$ ./gradlew perfJar
$ java -cp build/libs/disruptor-perf-*.jar com.lmax.disruptor.sequenced.OneToOneSequencedThroughputTest
----

=== Running JMH Tests

There are also https://github.com/openjdk/jmh/[JMH Benchmarks] for testing the performance of the Disruptor, these can be run with a gradle command

[source,shell script]
----
$ ./gradlew jmh
----

==== Production baseline on JDK 25

`ProductionSequencerBenchmark` measures the production sequencers with one publishing thread,
for both producer types, two buffer sizes and single/batch publication.
It advances a synthetic consumer sequence after publishing; it does not measure consumer processing,
producer contention or end-to-end latency.
Use `SingleProducerSingleConsumer` and `MultiProducerSingleConsumer` for the existing threaded pipelines.

[source,shell script]
----
$ ./gradlew jmh '-PjmhIncludes=com.lmax.disruptor.ProductionSequencerBenchmark.*' -PjmhProfilers=gc
----

Results are written to `build/reports/jmh/result.json`.
The defaults use two forks, five one-second warmup iterations and five one-second measurement iterations.
The `JMH baseline` workflow also measures the threaded pipelines, but shared CI runners should be used
for execution checks rather than performance acceptance decisions.

For a short execution check only:

[source,shell script]
----
$ ./gradlew jmh '-PjmhIncludes=com.lmax.disruptor.ProductionSequencerBenchmark.*' -PjmhForks=1 -PjmhWarmupIterations=1 -PjmhIterations=1 -PjmhWarmupTime=200ms -PjmhIterationTime=200ms
----

Compare unchanged and modified code on the same machine, JDK, JVM arguments and power settings.
Keep the JSON results outside the repository before another run overwrites them.
Evaluate throughput, allocation and latency separately; this throughput baseline does not establish p99 latency.
Run `./gradlew test` and the production concurrency checks before accepting a memory-ordering change:

[source,shell script]
----
$ ./gradlew jcstress -Pmode=quick '-PjcstressTests=com.lmax.disruptor.Production.*'
----

The JCStress task defaults to two CPUs and disables affinity for portability.
Use `-PjcstressCpus=8 -PjcstressAffinity=GLOBAL` on a suitable Linux benchmark host.
A passing stress run is evidence for the tested environment, not a proof for every architecture.

==== Producer assertions

Single-producer thread ownership is checked when Java assertions are enabled.
The check binds a sequencer to the first thread calling `next`; another thread is rejected before it claims a sequence.
Ownership is stored on the sequencer, so separate sequencers do not share a lock or retain each other through a global registry.
This diagnostic check does not make `ProducerType.SINGLE` safe for concurrent producers.

[source,shell script]
----
$ ./gradlew jmh '-PjmhIncludes=com.lmax.disruptor.ProductionSequencerBenchmark.publishSingle' -PjmhAssertions=true
----

Compare both assertion-enabled and assertion-disabled runs.
An improvement with `-ea` measures the diagnostic path; it does not imply a faster assertion-disabled production pipeline.
The benchmark uses independent sequencers per thread, so running its JMH jar with `-t 4` measures four independent producers,
not four producers sharing a single-producer sequencer.

==== Blocking Publication and Notification

`BlockingPublicationBenchmark` uses one platform consumer and the JMH publisher threads.
It selects a single-producer sequencer for one publisher and a multi-producer sequencer for more publishers.
Every consumed payload is checked against its sequence, and teardown checks that all published events were consumed.
The `waitStrategy` parameter compares `BLOCKING`, experimental `LITE_BLOCKING` and `BUSY_SPIN`.

[source,shell script]
----
$ ./gradlew jmhJar
$ java -jar build/libs/disruptor-4.0.0.jdk25-SNAPSHOT-jmh.jar 'com.lmax.disruptor.BlockingPublicationBenchmark.publish$' -t 1 -p waitStrategy=BLOCKING -f 5 -wi 3 -i 5 -w 1s -r 1s -prof gc -prof com.lmax.disruptor.ProcessCpuProfiler -jvmArgs '-da -Xms256m -Xmx256m' -rf json -rff /tmp/blocking-1p.json
----

Repeat with `-t 4` for 4P1C. Throughput and sample-time modes run separately.
Sample-time percentiles describe the publication call, including waiting for ring capacity;
they are not event processing completion percentiles.
`process.cpu` reports average process CPU usage in equivalent fully busy cores, including consumer and JVM work.
For throughput results, divide CPU usage by events per second to compare CPU time per event.

For a matched target rate, `publishPaced` submits batches every millisecond:

[source,shell script]
----
$ java -jar build/libs/disruptor-4.0.0.jdk25-SNAPSHOT-jmh.jar 'com.lmax.disruptor.BlockingPublicationBenchmark.publishPaced$' -t 4 -p waitStrategy=BLOCKING -p eventsPerMillisecond=1000 -f 5 -wi 3 -i 5 -w 1s -r 1s -prof com.lmax.disruptor.ProcessCpuProfiler -jvmArgs '-da -Xms256m -Xmx256m' -rf json -rff /tmp/blocking-paced.json
----

This targets four million events per second in periodic bursts, not uniformly spaced arrivals.
Check the achieved throughput before interpreting CPU usage at a matched load.
If the ring or generator falls behind, the achieved rate can miss the target; this does not establish an overload latency SLO.
Use `ThreadModelComparison` for completion latency under its documented admission limits.

`bufferSize` defaults to `65536`; smaller values such as `16` and `64` exercise capacity pressure.
`handlerWork` defaults to `0`; a value such as `256` adds dependent arithmetic operations in the consumer.
`handlerPauseNanos` defaults to `0`; use `1000000` with a small ring to simulate a consumer that sleeps for 1 ms per event.
This models a slow consumer, not an external I/O service. Configurations requiring more than five seconds
to drain the configured sleep across a full ring are rejected.
Compare completion latency as well as publication-call latency: a change in notification frequency can alter batching
and thread scheduling even when publication microbenchmarks and correctness checks improve.

=== Platform and Virtual Threads

`ThreadModelComparison` measures persistent producer/consumer pipelines in a separate JVM.
Producer and consumer thread kinds are selected independently.
Each pipeline has one producer and one consumer, so `ProducerType.SINGLE` remains valid for either thread kind.
This does not model creating a new virtual thread for every request.

[source,shell script]
----
$ ./gradlew threadModel -PthreadProducer=VIRTUAL -PthreadConsumer=PLATFORM -PthreadWait=BLOCKING -PthreadWorkload=CPU -PthreadStreams=1
----

Options:

* `threadProducer`, `threadConsumer`: `PLATFORM` or `VIRTUAL`.
* `threadWait`: `BLOCKING` or `BUSY_SPIN`.
* `threadWorkload`: `CPU` (64 dependent arithmetic rounds) or `WAIT` (a 1 ms sleep per event).
  `WAIT` simulates blocking I/O wait; it does not measure a database, socket or remote service.
* `threadStreams`: independent pipelines, default `1`; use `16` to examine oversubscription.
* `threadInFlight`: admitted events per pipeline, default `16`, range `1..256` with a fixed 1024-slot ring.
* `threadWarmupSeconds`, `threadMeasureSeconds`: defaults `2` and `3`.
* `threadOutput`: JSON output path, default `build/reports/thread-model/result.json`.

Warmup and measurement use the same payload validation, histogram recording and handler work.
The reported window uses fresh histograms without resetting counters while workers are running.
Every worker reaches a blocking start barrier before the warmup begins.
Worker failures and shutdown timeouts fail the run.

`eventsPerSecond` counts events admitted and completed inside the measurement window.
`p99Micros` measures admission to handler completion, including ring access, queueing and handler work;
it excludes waiting for the admission semaphore, which bounds outstanding work.
This is a closed-loop experiment, not an open-loop overload/SLO measurement.
`censored` counts admitted events not completed before the deadline; these are excluded from percentiles.
`cpuCores` is process CPU time divided by elapsed CPU sampling time: `1.0` means one fully busy core,
including scheduler, measurement and GC work.
The JSON also records actual worker kinds, scheduler parallelism, JDK and per-pipeline completion counts.

`NO_PROGRESS` means no event completed during measurement; `PARTIAL_PROGRESS` means at least one pipeline completed no events.
Both indicate a liveness problem. Percentiles from progressing pipelines must not be interpreted as covering stalled pipelines.
In particular, enough virtual consumers using `BUSY_SPIN` can occupy the carrier threads and prevent producers from running.
The main control thread is a platform thread, so it can still stop the experiment.

For repeated comparisons, build `perfJar` and start a new JVM for each configuration:

[source,shell script]
----
$ ./gradlew perfJar
$ java -da -Xms256m -Xmx256m -cp build/libs/disruptor-perf-4.0.0.jdk25-SNAPSHOT.jar com.lmax.disruptor.ThreadModelComparison VIRTUAL PLATFORM BLOCKING CPU 1 16 2 3 /tmp/thread-model.json
----

The manual `Platform and virtual thread comparison` workflow runs all 32 combinations of thread kinds,
wait strategies, workloads and 1/16 pipelines twice in fresh JVMs.
Shared CI results verify execution; use an otherwise idle target machine and repeat runs for performance decisions.
Keep machine, JVM arguments and carrier parallelism consistent, and compare throughput, p99, censored events and CPU together.

=== Isolated CPU benchmarking

Some JMH Benchmarks can be run on machines with isolated cpus to get results with less error.

Build the `jmhJar` on your development machine and transfer it to your benchmarking machine with isolated cpus:

[source,shell script]
----
dev-machine /path/to/disruptor $ ./gradlew jmhJar
dev-machine /path/to/disruptor $ scp dev-machine:build/lib/disruptor-*-jmh.jar bench-machine:
----

Assuming a system set up with isolated cores, e.g.

[source,shell script]
----
bench-machine ~ $ cat /proc/cmdline
... isolcpus=31,33,35,37,39,41,43,45,47,7,9,11,13,15,17,19,21,23 nohz_full=31,33,35,37,39,41,43,45,47,7,9,11,13,15,17,19,21,23 ...
----

And the system may have a `cpuset` setup to split application threads from sharing cpus with kernel code:

[source,shell script]
----
bench-machine ~ $ cat /cpusets/app/cpus
5,7-23,29,31-47
----

You can run the benchmarks taskset to some of those cpus so that Java threads (like GC and complication) run on some cores
and JMH Benchmark threads are pinned to isolated cpus using the following command (which is running just the one benchmark, `MultiProducersSequencerBenchmark`):

[source,shell script]
----
bench-machine ~ $ cat runBenchmarks.sh
#!/bin/bash
JAVA_HOME=/opt/jdk-25
ISOLATED_CPUS=7,9,11,13,15,17,19,21,23 $JAVA_HOME/bin/java -jar ./disruptor-4.0.0.jdk25-SNAPSHOT-jmh.jar -rf json -rff /tmp/jmh-result.json -foe true -v NORMAL -prof perf -jvmArgsPrepend -Xmx256m -jvmArgsPrepend -Xms256m -jvmArgsPrepend -XX:MaxDirectMemorySize=1g $@

bench-machine ~ $ sudo cset proc -v --exec app -- taskset -c 5,8,10,12,14,16,18,20,22,29,32,34,36,38,40,42,44,46 ./runBenchmarks.sh MultiProducersSequencerBenchmark
----
